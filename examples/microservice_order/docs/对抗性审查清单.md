# 对抗性审查清单

## 模型通过能说明服务代码正确吗？

- 质疑：模型与实际代码可能不同。
- 事实：BFS 只读取显式 JSON 模型；可选轨迹检查另读取独立本地程序实际执行时采集的状态，不提取源码或执行 HTTP 接口。
- 答辩要点：模型 PASS 限于声明模型；轨迹 PASS 限于已记录的这次顺序执行。正确模型能配合轨迹检查发现程序漏掉付款守卫，但这不是对全部代码行为的证明。
- 待补写位置：真实服务采集、模型抽象映射与日志完整性验证。

## 轨迹真的是程序执行产生的吗？

- 质疑：是否只是根据模型手写一份符合规则的日志，再验证自己？
- 事实：order_program.py 不读取模型；在实际动作执行前后采集 paid/shipped。Order 有付款检查，BuggyOrder 的 ship 故意遗漏该检查，两者用同一正确模型核对。
- 答辩要点：正常轨迹通过；缺陷程序的未付款发货轨迹失败，定位第 1 步并关联实际违反的 REQ-ORDER-001。采集代码、状态字段是否准确仍须人工检查。
- 待补写位置：README 的两组演示命令及本次生成的报告、轨迹哈希。

## 连续性与哈希能证明日志没有遗漏吗？

- 质疑：日志可能漏记动作，或没有暴露所有影响业务的状态。
- 事实：检查器要求全部声明变量和相邻记录连续，哈希标识所读文件；不能发现全部保持可见状态不变的漏记动作，也不能认证采集来源。
- 答辩要点：逐项检查程序状态到模型变量的映射，确认所有业务动作均采集；未观测状态、并发、拒绝请求和网络行为列为未覆盖范围。
- 待补写位置：接入真实系统时的采集点、状态映射及实例关联说明。

## 付款后停止的轨迹能通过吗？

- 质疑：只记录正常前半段会不会被误认为业务完成？
- 事实：轨迹要求末尾匹配声明的 terminal；只有 pay 的合法轨迹返回 INCONCLUSIVE，第二层退出 1。
- 答辩要点：合法前缀和完整业务执行分开判定；模型失败或搜索受限时，单条轨迹通过也不能覆盖模型结果。
- 待补写位置：references/configuration.md 中的轨迹判定和报告范围。

## 执行前缀是最短反例吗？

- 质疑：轨迹失败报告是否也证明了全局最短违规路径？
- 事实：BFS 的反例按动作数最短；轨迹检查只核对给定顺序，定位本次运行的首次违规步骤，保留截至该处的实际记录。
- 答辩要点：执行前缀没有模型全局最短的含义，模型反例和运行证据分别表述。
- 待补写位置：报告的 counterexample 与 execution_prefix 字段及 README 说明。

## 为什么称为模型检查？

- 质疑：是否只是挑选少数测试样例？
- 事实：从初始状态按全部启用转换做广度优先搜索，直到可达状态穷尽。
- 答辩要点：模型域有限，完成搜索后检查范围覆盖全部可达状态；发现违例时给出最短状态路径。
- 待补写位置：references/configuration.md 中的变量域、转换与不变量语义。

## 状态上限会不会产生假通过？

- 质疑：大型模型在中途停止也可能没见到违例。
- 事实：触及 max_states 时返回 INCONCLUSIVE，complete=false，第二层门禁返回失败退出码。
- 答辩要点：“暂未发现”不会被当作穷尽证明。
- 待补写位置：如扩到更大模型，再评估 Alloy/SMT 等后端。

## 终止状态和死锁如何区分？

- 质疑：付款并发货后没有后续动作是否被误判？
- 事实：terminals 显式声明允许结束的状态；其他无启用转换的可达状态判为死锁。
- 答辩要点：允许结束与异常阻塞分别编码；本工具不证明最终一定发货等活性性质。
- 待补写位置：需要活性结论时另加时序性质与公平性假设。

## 一个通过模型足以验证检查器吗？

- 质疑：检查器是否会对任何模型都报告通过？
- 事实：负对照模型删除付款守卫，必须返回 FAIL 和 initial → ship 的反例。
- 答辩要点：正例验证正确流程，负例验证违例检测能力，回归检查也覆盖初始违例、死锁和资源上限。
- 待补写位置：运行 evals/check_regressions.py；如需证据留存，使用 --output 生成本地报告。
